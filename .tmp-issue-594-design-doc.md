## 1. Document-based app design (the decision this issue adds)

### What is "the document"?

Codex's on-disk hierarchy is **Workspace → Notebook → files**, and it's already filesystem-rooted, not virtual:

```python
class Workspace(SQLModel, table=True):
    path: str = Field(unique=True)   # absolute filesystem path — a workspace IS one folder

class Notebook(SQLModel, table=True):
    workspace_id: int = Field(foreign_key="workspaces.id")
    path: str                        # relative path from workspace.path — a subfolder
```

(`backend/codex/db/models/system.py:114-115,226`). A **Workspace is one folder** (e.g. `~/Documents/Codex/Lab Notebook/`); each **Notebook is a subfolder** of it with its own `.codex/notebook.db`. So "folder-as-document" maps cleanly to **the Workspace folder**, not the Notebook — a Notebook alone isn't the unit a user would pick in an Open panel; a Workspace is.

### Recommendation: `NSDocument` as a thin OS-integration wrapper around a Workspace folder, not a data model

The classic `NSDocument` contract assumes the app is the *sole writer*: content lives in memory, `isDocumentEdited` tracks dirty state, `write(to:ofType:)` performs the save, and autosave/versions manage history. That contract is wrong for Codex on its face — Goal 2 in the existing doc is "edit with any external editor, watcher syncs," meaning the filesystem is the source of truth and can change without the app ever calling `write(to:)`. Adopting textbook `NSDocument` would fight the watcher (whose whole job is reacting to writes the document object didn't make).

The fix is to use `NSDocument` for what only it gives you — Launch Services integration — and disable everything that assumes app-owned writes:

| `NSDocument` feature | Use it? | Why |
|---|---|---|
| File → Open Recent, `NSDocumentController` open-dedup | **Yes** | Free, and dedup matters here specifically: opening the same workspace folder twice would start two FSEvents watchers and two in-process indexers racing on the same `.codex/notebook.db` files. `NSDocumentController.document(for:)` gives single-instance-per-URL for free. |
| One window per document, window restoration | **Yes** | Matches "one Workspace = one window with a notebook sidebar" from the existing doc's model, now backed by the standard window-controller machinery instead of hand-rolled window management. |
| Dock/Finder proxy icon, drag-icon-out-of-titlebar, "Move to…"/"Duplicate"/"Show in Finder" | **Yes** | Standard, expected affordances for a folder-backed app; costs nothing extra since the URL is already known. |
| Security-scoped bookmarks for the workspace folder | **Yes** | Needed regardless of sandboxing today, because it's the mechanism that survives macOS resetting non-sandboxed-but-TCC-gated folder access across relaunches, and is required outright if App Store distribution (Non-Goal 4, revisit-on-demand) ever happens. |
| Dirty-state tracking (`isDocumentEdited`, `updateChangeCount`) | **No — hardcode `false`** | There is no undo-manager-mediated edit stream to track; every write already lands on disk via the API/watcher path the instant it happens. A dirty flag here would be actively misleading ("unsaved changes" that don't exist). |
| Autosave-in-place, Versions (Time Machine-style document versions) | **No** (`autosavesInPlace = false`) | Redundant with git-based notebook history (existing doc §Sync) and actively wrong for a folder containing another program's live SQLite file — NSDocument's snapshot-on-autosave model doesn't know how to correctly snapshot a `.codex/notebook.db` mid-write. |
| `read(from:ofType:)` / `write(to:ofType:)` as the load/save path | **No — override as a no-op handshake** | `read(from:)` does nothing but record the URL and hand it to `CodexEngine` to open (start the watcher, open the notebook DB); there is no in-memory document model to marshal. |

Net effect: `CodexWorkspaceDocument: NSDocument` is a thin shim — maybe 100 lines — that exists purely so the OS treats a Codex workspace folder as a first-class document type, while the actual state management stays exactly where the existing doc puts it (`CodexEngine`, FSEvents, the notebook DB). This is additive to the existing single-window/sidebar UI model, not a competing one: it doesn't change what the window shows, only how the OS discovers, opens, and remembers it.

### Document type registration

`Info.plist` declares a `CFBundleDocumentTypes` entry for `com.codex.workspace` bound to a **folder-typed UTI** (`public.folder` conforming, `LSTypeIsPackage = false` so it stays a browsable Finder folder rather than becoming an opaque bundle — users must be able to `cd` into it, point Git at it, and open files in other editors, per Goal 2). This also registers Codex as a Finder "Open With" option for any folder containing a `.codex/` subdirectory, and is what backs the "drag a folder onto the Dock icon" flow already in the existing doc's P0 list.

### What doesn't get this treatment

Individual `.md` files opened via Quick Look or "Open With → Codex" from Finder are **not** separate documents — they resolve to "open the owning Workspace document, scroll to that block" (a `codex://` deep link), consistent with the existing doc's Non-Goal 1 (no per-file native editor).

## 2. Swift UI shell architecture wrapping web content

Endorsing the existing doc's conclusion without re-litigating it: **hand-built Swift/AppKit shell hosting the Vue SPA in `WKWebView`**, engine ported to Swift and run in-process via a `WKURLSchemeHandler` (no localhost port, no PyInstaller sidecar). See `docs/design/mac-app.md` §"Architecture Choice" for the full Electron/Tauri/Swift/native-rewrite comparison and the sizing table for the ~13-14K LOC Python→Swift port. Section 6 below restates the alternatives for completeness since the issue asks for them explicitly, but doesn't re-derive them.

One addition specific to the `NSDocument` decision above: the shell's `NSWindowController` for a `CodexWorkspaceDocument` owns exactly one `WKWebView` instance pointed at `app://<workspace-id>/`, so multiple open workspaces are multiple fully-isolated `WKWebView`s (separate `WKWebsiteDataStore` per document, since nothing about workspace A's JS state, IndexedDB cache, or in-flight requests should leak into workspace B's).

## 3. Local filesystem vs. web state sync strategy

Two independent sync axes exist and shouldn't be conflated:

**Axis A — disk ↔ in-app index (always on, single-writer).** Covered fully by the existing doc's "File watching" section: one `FSEventStream` per open Workspace, ported 1:1 from `watchdog`'s FSEvents backend already in use (`backend/codex/core/watcher.py`), feeding the same `.codex/notebook.db` sync logic. This is not really "sync" in the conflict-prone sense — there's exactly one writer (the local disk) and one reader (the in-process index), so it's closer to cache invalidation than sync.

**Axis B — local workspace ↔ remote server (opt-in, multi-writer).** This is where "local-first vs. server-first" actually applies, and where I'm extending the existing doc rather than repeating it — see §6 (Conflict Resolution) below, which ties directly into Epic #522's S3-as-source-of-truth design for shared workspaces.

## 4. WKWebView embedding and JS bridge

**Configuration:**
- `WKWebViewConfiguration.urlSchemeHandler(_:forURLScheme: "app")` registered for a custom scheme serving the built SPA's static assets and dispatching its `/api/v1/*` fetches to in-process `CodexEngine` handlers (existing doc §"In-process embedding"). The frontend's `services/codex.ts` base URL simply becomes `app://` instead of `http://localhost:8765` — no other frontend change.
- **CSP**: because the desktop build drops the vestigial dynamic plugin-loading path (existing doc §"Plugins in the desktop app"), the WebView can run under a strict `Content-Security-Policy` with `script-src 'self'` and no `unsafe-eval`/remote script origins — no runtime-fetched executable code in a process that also holds filesystem access and agent API credentials.
- `WKWebView.underPageBackgroundColor` and `.setValue(false, forKey: "drawsBackground")` tuned to avoid a white flash on window resize/dark mode, a common WKWebView-in-native-shell rough edge.
- Inspectable in debug builds only (`isInspectable = true` gated behind `#if DEBUG`), so Safari Web Inspector works during development without shipping it in release builds.

**JS bridge (native → web and web → native):**
- **Native → web** (push events: watcher changes, agent/task progress): `webView.evaluateJavaScript(...)` dispatching `CustomEvent`s the frontend's existing WebSocket-service abstraction subscribes to via a small adapter — the frontend doesn't need to know its "socket" is actually a bridge call (existing doc §"Push events"). This is the replacement for the WebSocket channel, which can't ride a custom-scheme `WKWebView`.
- **Web → native** (menu commands, native dialogs, Spotlight/Quick Look coordination): a `window.codexShell` object injected via `WKUserScript` at document start, backed by `WKScriptMessageHandler` for the handful of calls that need to leave the page (`revealInFinder(path)`, `showShareSheet(url)`, `requestNotificationPermission()`, `openExternal(url)`). Kept intentionally small — most functionality goes through the existing `/api/v1/*` surface, not a bespoke bridge API, so the bridge doesn't become a second, undocumented API surface to keep in sync with the Python server.

**Offline support and sync queue:** for **local workspaces**, "offline" isn't a distinct mode — there's no server round-trip on the hot path at all (the engine is in-process), so the app is offline-capable by construction. For **remote-attached workspaces** (existing doc §"Sync with a Remote Server" mechanism 1), the SPA already does classic client-server fetches against a remote base URL; true offline editing of remote workspaces is explicitly out of scope for v1 (same doc, same section) — the app behaves like the web app does today (requires connectivity), which sidesteps building a write-queue/replay mechanism until it's justified by real usage of remote-attach.

**Handling web app updates without an App Store release:** the SPA ships **inside** the signed app bundle (existing doc's "single binary" property), not fetched from a CDN at runtime — so an SPA update is an app update, delivered via Sparkle (§7 below), not a separate release channel. This is deliberate: fetching frontend code at runtime from an external origin would reintroduce the "runtime-fetched executable code" attack surface the CSP tightening in this section just closed, for a single-developer-adjacent update cadence that doesn't need it. If update latency between SPA and Python-server releases becomes a real problem, revisit — but don't build a second update channel speculatively.

## 5. Native integrations

Endorsing the existing doc's prioritized P0/P1/P2 list (`docs/design/mac-app.md` §"macOS Integration Features") — Dock/menu bar, `codex://` deep links, Spotlight via Core Spotlight mirroring the existing `SearchIndex`, a Quick Look extension rendering frontmatter + Markdown statically (custom blocks as labeled placeholders, not executed), and a menu-bar quick-capture window as the single highest-leverage feature. Two additions the issue calls out that the existing doc under-specifies:

- **Finder Quick Actions / Services**: "New Codex Note from Selection" (existing doc, P2 #11) should be implemented as a **Finder Sync Extension `NSExtension` of type `com.apple.services`**, not a full Finder Sync provider (which is for cloud-storage-style badge/context-menu integration and is much heavier machinery than a single Quick Action needs). Scope for v1: right-click a `.md` file or text selection → "Add to Codex Notebook…" with a notebook picker, POSTing through the same in-process API the quick-capture window uses.
- **Drag-and-drop**: dragging files/images from Finder onto a BlockView page should go through the existing upload API path unchanged (`WKWebView` forwards native drag sessions to the page's HTML5 drag-drop handlers by default) — worth an explicit test pass since WKWebView's drag interop with native `NSDraggingInfo` sessions (e.g. dragging *out* of the app, or dragging *from* Finder while a modifier key is held) has historically had rough edges worth catching before v1, not a design change.

## 6. Conflict resolution between local and server

This is the one place the existing `mac-app.md` doc is genuinely thin (it lists mechanisms but doesn't resolve local-first-vs-server-first), and it's where Epic #522 (S3 sync for shared workspaces) already made the relevant decision at the server level — the desktop app should inherit it rather than invent a second conflict model:

**Personal (local-only) workspaces**: no conflict is possible by construction — the local disk is the *only* writer (Axis A above), so "local-first vs. server-first" doesn't apply. This is the common case and needs no policy.

**Remote-attached workspaces (existing doc's mechanism 1, client-server, no local copy)**: also no local/remote conflict — there's no local copy to diverge from; it's a thin client against the server's existing last-write-wins REST semantics, unchanged from the web app today.

**Git+S3-synced personal workspaces (existing doc's mechanisms 2-3, multi-machine same-user)**: conflicts are surfaced, not silently resolved — a pull that can't fast-forward flags the conflicting files in the block tree for resolution in an external editor (existing doc, unchanged). No CRDTs. **Server-first does not apply here because there usually is no server** — sync is machine-to-machine via a git remote.

**Shared/org workspaces (Epic #522 territory — `Workspace.org_id` set)**: this is where the desktop app must plug into the server's model rather than define its own, because §3.1 of `docs/design/multi-user-multi-org.md` already made the call: **for shared workspaces, S3 is canonical; local checkouts (including this Mac app's Workspace folder) are working copies, not sources of truth.** Concretely for the desktop app:
- The local Workspace folder for a shared workspace is populated the same way the server's own working copy is (§3.2 of that doc) — it's a sync target, not the origin.
- Writes go through the same compare-and-swap-by-`s3_version_id` flow (§3.4): the client's push includes the base version it last saw; a stale base doesn't reject the write (both versions are kept, S3 versioning is on) but the sync journal marks a **conflict**, surfaced identically to how the personal-git path surfaces conflicts — a `name (conflict YYYY-MM-DD).md` sibling file plus a conflict notification, not a merge UI. **This directly answers "local-first vs. server-first": neither wins — both are kept, deterministically, and the human resolves.** Consistent with that design doc's explicit rejection of CRDTs/OT for the same reason (single-author-journal-shaped conflict rates don't justify the complexity).
- Credentials for this sync are the same short-lived STS tokens vended by `POST /api/v1/workspaces/{ws}/sync/credentials` (§3.3) — the desktop app never holds long-lived S3 keys, same as any other client.
- This means shared-workspace sync is **not** part of the Mac app's v1/Phase-1-4 scope as scoped in the existing doc (Phase 4 there covers git+S3 for *personal* multi-machine sync, which predates and is simpler than Epic #522's shared-workspace model). Shared-workspace desktop sync should be sequenced **after** Epic #522 ships server-side, as its own phase, so the desktop app is a client of an already-decided sync journal/conflict format rather than a second implementation racing the server's.

## 7. Build and distribution approach

Endorsing the existing doc's §"Distribution" as-is: Developer-ID signed + notarized DMG, Sparkle 2 for updates, Homebrew cask as a secondary channel, Mac App Store deferred (revisit once security-scoped bookmarks — needed anyway per §1 above — and an updater swap are in place). One point worth making explicit given §1's `NSDocument` decision: security-scoped bookmarks are now **not** purely an App Store-readiness item to defer — they're needed the moment `NSDocumentController` manages "Open Recent" across relaunches for folders outside the sandbox-free-access set (e.g. a workspace the user keeps somewhere other than `~/Documents`), so bookmark persistence should land in Phase 1, not be deferred to an App Store push.

## 8. Alternative architectures and trade-offs

Restating the existing doc's shell-layer comparison plus the issue's "no native app" baseline, in one table:

| Option | UI reuse | Native feel | Distribution weight | Verdict |
|---|---|---|---|---|
| **Pure web app in browser** (status quo) | Full | None (no Dock icon, Spotlight, Quick Look, menu bar) | Zero — nothing to ship | Baseline. Zero native integration is the entire reason this issue exists; not viable as the answer. |
| **Electron-style wrapper** | Full | Weak | ~150MB+ (bundled Chromium) | Rejected — wrong weight class for a journal app; existing doc §"Architecture Choice". |
| **Tauri v2** | Full | Good | ~15-40MB | Rejected for a Mac-first product specifically — its cross-platform reach and prefab plumbing (updater, tray, notifications) are exactly the well-trodden small patterns AppKit already provides directly, so Tauri buys an abstraction layer over APIs the feature list needs raw access to anyway (Spotlight, Quick Look, security-scoped bookmarks). Reconsider if/when a Windows or Linux desktop app is actually committed to. |
| **Swift/AppKit shell + WKWebView** (recommended) | Full | Best available without a full rewrite | Smallest shell + ported engine | Recommended — see existing doc for full rationale. |
| **Full native SwiftUI rewrite** | None | Best possible | Smallest | Rejected for v1 on surface breadth (BlockView, MarkdownViewer's custom blocks, agent chat, themes all need Swift equivalents for zero v1 user benefit) — but flagged in the existing doc as *more feasible than it looks* now that the plugin system no longer needs to host arbitrary third-party Vue components. Worth revisiting for a future iOS companion, not v1 Mac. |
| **Python sidecar (PyInstaller)** | Full | Same as Swift shell (same WKWebView) | Same shell + ~100MB+ Python runtime | Explicitly the *fallback*, not the primary plan — existing doc's "Engine" section gives the reasoning (packaging fragility under notarization, process supervision tax, a localhost attack surface, cold-interpreter startup) and confirms the shell/engine seam is identical either way, so this remains available without touching frontend or shell work if the Swift port stalls. |

## Open questions from the issue — answered

1. **"How does folder-based editing interact with multi-user features?"** — it doesn't, for shared workspaces, by design: §6 above ties this to Epic #522 — local folders are working copies for shared workspaces, S3 is canonical, and the desktop app is a client of the server's already-decided sync/conflict model, sequenced after that epic ships.
2. **"Should local-first or server-first win during conflicts?"** — neither; §6's answer is deterministic dual-retention (both versions kept via S3 bucket versioning + a conflict-copy file), not a winner-take-all policy, matching the multi-user design doc's explicit CRDT/OT rejection for this problem shape.
3. **"What happens when the folder is on a network drive or cloud sync folder?"** — the existing doc already covers the iCloud Drive case (dataless/evicted placeholder files must be treated as "present but not readable yet," not deletions — §"File watching" point 2). Extending that: **Dropbox/Google Drive-style folders and SMB/AFP network drives should not be blocked, but should be flagged** — a warning banner on open, not a hard restriction, because (a) two independent sync engines (Codex's FSEvents watcher + Dropbox's own file-system hooks) racing on the same files is a known source of partial-write corruption for any app that assumes atomic local writes, and (b) network-drive FSEvents delivery is unreliable enough that the watcher may miss events entirely, silently desyncing the index from disk. v1: detect known cloud-sync folder roots (`~/Library/CloudStorage/*`, `~/Dropbox`) and non-local volume types, surface a one-time warning, don't block.
